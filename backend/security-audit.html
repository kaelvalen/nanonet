Kapsam: nanonet/backend (Go + Gin). Bu rapor kod okuması temellidir; runtime/infra egress policy bilinmediği için outbound yüzeyler “varsayılan açık” kabul edilmiştir.

En acil aksiyonlar: (1) REST + WS agent tarafında ?token= desteğini kaldırın; yalnızca Authorization: Bearer kabul edin. (2) Synthetic probe + webhook URL’leri için SSRF kontrolleri ve/veya egress kısıtı ekleyin. (3) CORS allowlist mantığını düzeltin; allowlist dışı Origin’de Access-Control-Allow-Origin set etmeyin.

Detaylar

SSRF: Synthetic probe hedefleri doğrulanmıyor (HTTP/TCP)

CRITICAL
Etki
Yetkili bir kullanıcı, backend’in network erişimini kullanarak iç ağ hedeflerine (örn. 169.254.169.254, cluster servisleri, DB portları) HTTP/TCP istekleri attırabilir.
Kanıt
  • nanonet/backend/internal/probes/service.go — Create/Update path’inde allowlist/denylist yok
  • nanonet/backend/internal/probes/runner.go — p.Target’a doğrudan request/dial
Öneri
URL validasyonu + DNS/IP resolution sonrası private/reserved bloklama (DNS rebinding dahil), port allowlist, redirect limit + redirect hedef doğrulaması. Alternatif olarak probe runner’ı egress’i kısıtlı bir ortamda çalıştırın.

SSRF: Webhook/Slack/Discord URL’leri kısıtlanmıyor

HIGH
Etki
Kullanıcı tanımlı URL’lere backend’den POST → iç ağa erişim, metadata servislerine istek, internal panellere saldırı.
Kanıt
  • nanonet/backend/internal/notifications/dispatcher.go — postJSON her URL’ye POST
  • nanonet/backend/internal/notifications/handler.go — Create/Update path’inde URL kontrolü yok
Öneri
Generic webhook’u allowlist ile sınırlandırın (örn. Slack/Discord domainleri) veya opsiyonel/kapalı yapın. DNS+IP bloklama, redirect kapatma ve outbound proxy/egress policy ile zorlayın.

Bearer token kabulü query param üzerinden (token sızıntısı riski)

HIGH
Etki
Token URL içinde taşındığı için log/history/referrer üzerinden sızabilir.
Kanıt
  • nanonet/backend/internal/auth/middleware.go — c.Query("token")
  • nanonet/backend/internal/ws/handler.go — agent bağlantısında ?token= fallback
Öneri
Query param token desteğini kaldırın; yalnızca Authorization: Bearer kabul edin. WebSocket tarafında (dashboard) zaten “ilk mesajla auth handshake” var; agent için de header veya kısa ömürlü upgrade token tasarlayın.

CORS: izinli değilse bile Access-Control-Allow-Origin set ediliyor

HIGH
Etki
Allowlist dışı Origin’de bile header yazıldığı için beklenen CORS davranışı bozulur; Allow-Credentials ile riskli kombinasyonlar doğabilir.
Kanıt
  • nanonet/backend/pkg/middleware/cors.go — allowlist değilse frontendURL’ye fallback
Öneri
Allowlist dışı Origin’de Access-Control-Allow-Origin set etmeyin (veya 403). Vary: Origin ekleyin. Cookie auth yoksa Allow-Credentials kapatılabilir.

WebSocket CheckOrigin: Origin boşsa izin veriliyor

MEDIUM
Etki
Origin kontrolü, tarayıcı olmayan istemciler için boş Origin’e izin veriyor. Dashboard endpoint’i için daha strict olmak daha güvenli.
Kanıt
  • nanonet/backend/internal/ws/handler.go — Origin == "" ise true
Öneri
Dashboard WS için Origin’i zorunlu + allowlist doğrulama yapın. Agent WS için ayrı policy (ayrı upgrader/route) uygulayın.

Security scanner InsecureSkipVerify kullanıyor

MEDIUM
Etki
TLS doğrulaması olmadan istek atıldığı için MITM altında yanlış ölçüm ve riskli varsayılanlar.
Kanıt
  • nanonet/backend/internal/security/scanner.go — TLS dial + HTTP transport InsecureSkipVerify: true
Öneri
Prod’da doğrulamayı açın; gerekiyorsa explicit allowlist/flag ile self-signed istisnası tanımlayın.

HTTP security headers: CSP yok, bazı header’lar legacy

LOW
Etki
CSP eksikliği XSS etkisini artırır; bazı header’lar modern tarayıcılarda etkisizdir.
Kanıt
  • nanonet/backend/pkg/middleware/security.go — CSP yok; HSTS her ortamda set ediliyor
Öneri
CSP ekleyin; HSTS’yi sadece HTTPS/prod’da set edin; legacy header’ları gözden geçirin.
